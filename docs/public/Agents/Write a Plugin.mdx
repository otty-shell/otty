A plugin teaches OTTY an agent or a provider without any change to OTTY. It is a WebAssembly
component written in Rust, kept in your own GitHub repository, and installed by its users from a
link. When the agent changes its files, you ship a new release; OTTY picks it up.

**The rule:** everything that breaks when an agent or a provider updates (file names, field names,
JSON shapes, SQL, screen text, URLs) lives in the plugin. OTTY does the generic work: walking files
and re-reading only the changed ones, adding up tokens, counting an answer once, the "format
changed" verdict, prices, joining accounts and the whole interface.

**A plugin gives rows, OTTY sums.** A row is one fact as the agent wrote it: one answer of the model
with its time, model, provider, login, session, project and tokens; a limit or a balance a
provider told; a bill. Every total is OTTY's: today, this week, by project, by model, money, and
the numbers of one session or one project in their statistics. So your plugin never adds tokens
up, and the statistics always agree with the totals.

## Start from the template

Copy `plugins/template/` of the [OTTY repository](https://github.com/otty-shell/otty) into a new
repository. It is a working plugin over a made-up agent and a made-up provider:

| File                             | Holds                                                                    |
| -------------------------------- | ------------------------------------------------------------------------ |
| `otty-plugin.toml`               | The manifest: the plugin, its parts and their permissions.               |
| `src/lib.rs`                     | The plugin type and the `export!` line.                                  |
| `src/agent.rs`, `src/provider.rs` | One `impl Agent` and one `impl Provider`, with their tests.             |
| `src/needs.rs`                   | The needs the parts give, with their texts in OTTY's ten languages.      |
| `fixtures/`                      | Made-up files that stand for the home folder in tests.                   |
| `*.svg`                          | One icon per part.                                                       |
| `.github/workflows/release.yml`  | Builds and releases the plugin on a version tag.                         |

The SDK is not on crates.io yet. Depend on it by a tag of the OTTY repository:

```toml
[dependencies]
otty-plugin-sdk = { git = "https://github.com/otty-shell/otty", tag = "<OTTY release tag>" }
```

## The manifest

```toml
[plugin]
id = "example"                  # stable; a new id is a new plugin
name = "Example"
version = "0.1.0"               # equals the release tag without "v"
description = "A made-up agent and a made-up provider."
repository = "https://github.com/you/otty-plugin-example"
license = "Apache-2.0"
authors = ["You"]
wasm = "example.wasm"           # must be "<id>.wasm"

[api]                           # one contract version per kind of part: domain.part
agents.agent = "0.1"
agents.provider = "0.1"
language = "0.1"                # optional, of no domain: the plugin's texts come in several languages

[[agents.agent]]
id = "example-agent"            # saved by OTTY; never change it
name = "Example Agent"
icon = "example-agent.svg"
program = "example-agent"       # looked up on PATH
tested_version = "1.4.2"        # newest agent version this release was checked with

[agents.agent.permissions]
read = ["~/.example-agent*/**", "{EXAMPLE_AGENT_HOME}/**"]
env = ["EXAMPLE_AGENT_HOME"]

[[agents.agent.permissions.keys]]      # readable only with the keys replaced by handles
files = ["~/.example-agent*/auth.json", "{EXAMPLE_AGENT_HOME}/auth.json"]
fields = ["/api_key"]

[[agents.provider]]
id = "example-cloud"
name = "Example Cloud"
icon = "example-cloud.svg"
hosts = ["example.com"]         # keys found for these hosts go to this part
usage_page = "https://example.com/usage"
add_by_hand = true              # Add account offers this provider for a key no agent uses
# priced_as = "example_cloud"   # its name in the LiteLLM price table, when not the id

[agents.provider.permissions]
http = ["api.example.com"]
```

Each part belongs to a **domain** of OTTY, the place of the window it fills, and is written under the
domain's name: the agents and providers of Agents mode are the `agents` domain, so each
`[[agents.agent]]` and `[[agents.provider]]` is a **part** with its own id, icon and permissions, and
`[api]` names its contract as `agents.agent` and `agents.provider`. A part at the top level, such as
`[[agent]]`, is refused as an unknown field. A plugin may have any number of parts; a new part is a
new release. The permissions of a part apply only while
OTTY calls that part: above, the provider part may not read `~/.example-agent`, and the agent part
may not call `api.example.com`.

| Permission                       | Of     | Allows                                                                  |
| -------------------------------- | ------ | ----------------------------------------------------------------------- |
| `read`                           | both   | Listing and reading files that match the globs.                         |
| `write`                          | both   | Deleting files that match the globs.                                    |
| `sqlite`                         | agent  | Read-only queries of the databases that match.                          |
| `env`                            | both   | Reading these environment variables, and using them in globs as `{NAME}`. |
| `[[agents.<kind>.permissions.run]]`      | both   | Running `program` with arguments that match `args`, once or line by line. |
| `[[agents.<kind>.permissions.terminal]]` | both   | Running `program` with `args` in a hidden terminal.                     |
| `[[agents.agent.permissions.keyring]]`  | agent  | Reading the keyring entry `service` / `user` once the user allows the keyring; `fields` are its key fields. |
| `[[agents.agent.permissions.keys]]`     | agent  | Where keys are: JSON `fields` of `files`, a `column` of a `table` in `sqlite` databases (with `fields` for a JSON column), or `env` variables. |
| `http`                           | provider | HTTPS requests to exactly these hosts.                                |

Paths start with `~` or with a listed variable (`{XDG_DATA_HOME}/...`) and may not contain `..`.
Ids use lowercase letters, digits and dashes. Each part needs an icon: an SVG of at most 16 KiB with no scripts, links
or embedded images, drawn in one color with `currentColor`. Every part needs its contract
in `[api]`, and `[api]` may name no contract without a part, except `language`, which belongs to
the whole plugin ([below](#the-language)). Unknown fields are refused, so a
misspelt permission is never dropped silently.

## The code

One plugin type serves all its parts. All agent parts share one `impl Agent`, all provider parts one
`impl Provider`; OTTY passes the part's id with each call (`agent`, `profile.agent` or `provider`).
The traits and every type of the domain are in `otty_plugin_sdk::agents`; the host operations
(`files`, `http`, `keys`, `env` and the rest), `Need`, `Key` and `HostError` are at the root of the
SDK, since every domain uses them. The last line names the domain's parts the plugin serves, and must
match `[api]`:

```rust
// src/lib.rs
mod agent;
mod provider;

/// The plugin: one type serves every part its manifest lists.
pub struct Example;

otty_plugin_sdk::export!(Example with agents::agent, agents::provider, language);
```

A plugin with only agent parts and texts only in English writes
`export!(Example with agents::agent)` and has only `agents.agent` in `[api]`.

| `Agent`                                   | Gives OTTY                                                          |
| ----------------------------------------- | ------------------------------------------------------------------- |
| `profiles(agent)`                         | The agent's config folders on this computer, default first.         |
| `detect(profile)`                         | Logged in; `ProfileStatus::NotLoggedIn(need)` with the [need](#needs) that says how to log in; or no folder. |
| `version(profile)`                        | The version written in the newest files; `None` makes OTTY run `<program> --version`. |
| `logins(profile)`                         | Each login and key: its kind, where it sits, whom it is for (a provider name or a host), the account or email when the files say. |
| `session_places(profile)`                 | File globs or a database that hold the sessions. OTTY re-reads only what changed. |
| `read_sessions(profile, item)`            | What one file tells about its sessions: the id, and the folder and the title when the file names them. |
| `spend_places(profile)`                   | File globs or a database that hold the answers. OTTY re-reads only what changed. |
| `read_answers(profile, item)`             | Every answer of one file, of the whole history, with its tokens, an identity, and the session and the project it was given in, and the records seen and understood. OTTY makes the statistics of a session and of a project from these answers, reading for them only the files your session places tie to that session or project. |
| `launch(profile, session)`                | The commands for New session and Continue.                          |
| `login_refused(profile, login)`           | Optional: the [need](#a-refused-login) to show when a provider part refused a login this profile keeps. |

| `Provider`                        | Gives OTTY                                                               |
| --------------------------------- | ------------------------------------------------------------------------ |
| `account(provider, key, found)`   | Whose account the key is: account or organization id, email, plan.      |
| `numbers(provider, found, account, key, given)` | Limits, credits, extra usage, Left, Key limit, Spent this month; each optional. Read [any way you can](#numbers-any-way-you-can). |
| `read_bill(provider, found, account, key, given, days)` | Optional: the bill of an organization per UTC day.        |

### Numbers any way you can

The provider part reads an account's numbers, however it can get them: from the provider's server
with the key, or by asking the agent itself, such as `claude /usage` in a hidden terminal or the
limits Codex writes in its session files. `found` tells what OTTY found about the login: its kind,
its identity, and `found_in`, every profile the account was found in, each with the plugin and the
agent part that found it, its config folder, and `launch`, the command that part starts the agent
with there. Run that command with your own arguments, under the provider part's own `run` or
`terminal` permissions; while Agents mode is not on screen no program starts, and the next read on
screen asks again.

A key that is not at its place is a normal case, such as a Claude Code profile whose
`.credentials.json` is `{}` while Claude Code still works: using the handle fails with
`HostError::NotFound`. Try your other ways then. When no way works, answer numbers with nothing in
them, not an error; OTTY shows no limits. Every provider part that serves an account reads it:
when two plugins serve one provider, each reading is an account of its own, named with its plugin,
and the user hides the one they do not want.

A place is a glob and its kind, files or a database. OTTY lists the files of the places, keeps
what each file gave, and asks your part again only for a file that is new or whose size or change
time changed; a file that is gone drops what it gave. Your part keeps nothing between reads. The
`item` names the file with its size and change time as OTTY listed it. OTTY joins what all the
files tell about one session id: the latest time, and the folder and the title of the latest
record that names them. So a file may tell only a part, such as an index of titles: Codex names
its session files and `session_index.jsonl` as session places. A session no file gives a folder
is not listed, and one with no title shows its id. For a database, return every session it holds
from each of its files (the database and its write-ahead log).

Make every answer file a session place too, even one that only adds to a session, such as the file
of a helper agent: from it return just the session id, with no folder and no title. The statistics
of a session or a project read only the answer files tied to their sessions; while one answer file
is no session place, OTTY can not tell whose answers it holds and reads the whole history for every
panel, which is slow on a large history.

`key` is the account's own key; `given` holds the keys the user gave for the account after one of
your needs asked for them ([below](#keys-you-ask-for)). An optional function returns "not supported"
by default. Count records with `RecordCounts` (`add_understood`, `add_not_understood`,
`add_broken`, `saw_version`) so OTTY can tell a changed format from fewer tokens.

### Who served an answer

Give each answer the model as the provider names it and who served it, read from your agent's
settings and files: `ProviderRef::Id` with the provider's name as the agent wrote it, or
`ProviderRef::Host` with the host of its server when the agent names no provider. Pass the name
even when no plugin serves that provider, such as OpenCode's `google` or a local model; do not map
it to the providers you know. OTTY joins the name to the provider part with that id, and prices the
answer with the [LiteLLM](https://github.com/BerriAI/litellm) price table: the row of who served
it and the model (`openrouter/anthropic/claude-x`), else the row of the plain model name, the
maker's own price, else no price.

A provider part is known to the price table by its id. When the table names the provider otherwise,
give that name in the part's manifest: `priced_as = "gemini"` for a part whose id is `google`.

### Needs

Everything the user must do for your agent or provider, your part says itself, as a `Need`. OTTY
shows it as it is, with a small label naming your plugin, and its button does the need's action.
OTTY writes only the needs about plugins and its own permissions (an update waiting for an OK, a
part turned off, a key for a host no plugin serves, a plugin that failed, a changed format, the
keyring), never one about your agent.

```rust
use otty_plugin_sdk::env::in_language;
use otty_plugin_sdk::{Command, Need, NeedAction};

/// The title of `not_logged_in`, one text per language tag; the template has all ten.
const NOT_LOGGED_IN_TITLE: &[(&str, &str)] = &[("en", "Needs login"), ("ru", "Нужен вход")];

/// Nobody is logged in with the profile: the button runs `login` in a terminal tab.
pub(crate) fn not_logged_in(login: Command) -> Need {
    Need {
        id: "not-logged-in".to_string(),
        title: in_language(NOT_LOGGED_IN_TITLE).to_string(),
        text: in_language(NOT_LOGGED_IN_TEXT).to_string(),
        action: NeedAction::Run(login),
    }
}
```

| Field    | Holds                                                                                 |
| -------- | ------------------------------------------------------------------------------------- |
| `id`     | A name of the need, stable within the part, such as `not-logged-in`. Two reads that give the same id show one need, and it does not flicker between reads. Do not put a time or a count in it. |
| `title`  | What is needed, in a few words.                                                       |
| `text`   | Why, and what the button does.                                                        |
| `action` | One of the four actions below.                                                        |

| `NeedAction`        | The button                                                                  |
| ------------------- | --------------------------------------------------------------------------- |
| `Run(Command)`      | Runs the command in a new terminal tab, such as `codex login`, or the agent itself so it renews its login. The same rules as for `launch`. |
| `AskKey(KeyAsk)`    | Opens a field for a key. `KeyAsk` has a `slot` (your own name for the key, such as `admin`, or `None` for the account's own key, [below](#a-refused-key)), a `label` (the name of the field, which also names the button, "Admin key…"), a `hint` (one line under the field), an optional `prefix` the key starts with, such as `sk-admin-`, and an optional `https` `page` where the user makes the key. |
| `OpenPage(url)`     | Opens an `https` page in the browser, such as the page of new keys.         |
| `CopyReport(text)`  | Puts the text on the clipboard, such as a report for you.                  |

A part gives a need in two places:

- `ReadError::NeedsUser(need)`: the part can not read until the user does this, such as give a key
  it asks for, or make a new key because the provider refused the old one.
- `ProfileStatus::NotLoggedIn(need)` from `detect`: nobody is logged in with the profile. The need's
  `Run` is also what the profile's **Log in** menu item runs.

### Keys you ask for

A provider part that needs a key the account does not have, such as an admin key for an
organization's bill, answers `ReadError::NeedsUser` with an `AskKey` need. The user gives the key
once; OTTY keeps only where the user keeps it (a file or a variable) and from then on passes it to
`numbers` and `read_bill` in `given`, as a handle with its slot. `given_key(given, slot)` finds it:

```rust
use otty_plugin_sdk::agents::{AccountFacts, Bill, DayRange, LoginFacts, ReadError};
use otty_plugin_sdk::{GivenKey, Key, given_key};

fn read_bill(_provider: &str, _found: &LoginFacts, _account: &AccountFacts, key: &Key,
             given: &[GivenKey], days: &DayRange) -> Result<Bill, ReadError> {
    let bill_key = match key.has_prefix("ex-admin-").map_err(ReadError::Host)? {
        true => key,
        false => given_key(given, "admin")
            .ok_or_else(|| ReadError::NeedsUser(needs::bill_key()))?,
    };
    // ...read the bill with `bill_key`
}
```

When the provider refuses a key the part asked for, answer `NeedsUser` again with an `AskKey` under
the same slot, so the user replaces it.

### A refused key

When the provider refuses the account's own key (the `key` of the call), the new key belongs where
the old one sits, and `key.is_given_in_otty()` tells you which place that is. It is the one thing a
part learns about where a key came from:

- `true`: the user gave the key in OTTY, on **Add account** or in the field of an `AskKey`. Answer
  `NeedsUser` with an `AskKey` whose `slot` is `None`: OTTY opens the field with the place of the
  old key, saves the new place in its stead, and the next read gets the new key as `key`.
- `false`: OTTY read the key from a place of an agent, such as a field of its settings file, a
  variable, a keyring entry or its database. OTTY can not write there, so answer with an
  `OpenPage` need for the page of new keys, and say to put the new key where the agent keeps it.

```rust
fn refused_key_need(key: &Key) -> Result<Need, ReadError> {
    Ok(match key.is_given_in_otty().map_err(ReadError::Host)? {
        true => needs::replace_key(KEYS_PAGE),   // AskKey { slot: None, page: Some(KEYS_PAGE), .. }
        false => needs::new_key(KEYS_PAGE),      // OpenPage(KEYS_PAGE)
    })
}
```

A key the user gave under a slot is also given in OTTY: when it is refused, ask for it again under
its slot, never with `slot: None`, which would replace the account's own key. `slot: None` replaces
only the key of an account the user added; for an account an agent keeps, OTTY does not open the
field. In tests, `TestHost::given_key` makes a key given in OTTY, `TestHost::key_at` a handle to the
key at a place, read at each use as OTTY reads it, which may be not there, and `TestHost::key` one read from
an agent's place.

### A refused login

A provider part may read with a login an agent keeps, such as a ChatGPT or a Claude login. It does
not know which agent keeps it, so it writes no need for it: when the provider refuses the login, or
the part sees it expired, it answers `ReadError::LoginRefused`. OTTY then asks the agent part of
each profile that holds that login, through `Agent::login_refused(profile, login)`, and shows its
need on the profile with that plugin's label:

```rust
fn login_refused(profile: &Profile, _login: &LoginRef) -> Option<Need> {
    Some(needs::login_refused(login_run(profile))) // `example-agent login` in its folder
}
```

The login is passed too, so a part that keeps several logins can tell which one. The default gives
`None`; OTTY then shows its own need "The login was refused", with no button. When the provider
part asks the agent itself and its login expired there, give that need the same id, so the profile
shows it once.

### The language

Write the texts of your needs in the language of OTTY's interface, or in English. `env::language()`
gives it as a tag such as `en`, `ru` or `pt-BR`, at every call: it is the language OTTY shows now,
and it may change while your plugin is loaded. `env::in_language(texts)` picks one of your
translations, given as pairs of a tag and a text: the same tag, else the same language with another
region (`pt` for `pt-BR`), else English. OTTY's own languages are `en`, `zh-CN`, `zh-TW`, `ja`, `ko`,
`fr`, `de`, `es`, `pt-BR` and `ru`. The contract carries no translation tables: they live in your
plugin.

A plugin with translations also implements the optional `Language` trait, exports it
(`export!(Example with agents::agent, agents::provider, language)`) and names it in the manifest as
`[api] language = "0.1"`. It belongs to no part and no domain:

```rust
impl otty_plugin_sdk::Language for Example {
    /// The texts of the needs come in every language of OTTY.
    fn language_changed(_tag: &str) -> bool {
        true
    }
}
```

When the user changes the language, OTTY calls `language_changed` on every plugin that exports it.
When one answers `true`, OTTY reads Agents mode again at once, so its needs show in the new language
without a restart. The call has no permissions: it may only answer. A plugin without it is never
called, and its texts change at its next read.

### Host operations

The plugin reads and sends only through the SDK's functions. Each call is checked against the
permissions of the called part; a refused call returns `HostError::NotAllowed`.

| Function                                             | Does                                                     | Needs              |
| ---------------------------------------------------- | -------------------------------------------------------- | ------------------ |
| `files::list`, `files::read`                         | Paths, sizes and times; the bytes of a file up to 4 MiB. | `read`             |
| `files::lines(path, markers)`                        | Batches of complete lines holding a marker; zstd files decoded. | `read`      |
| `files::json_with_keys`                              | A key file as JSON, each key as `{"$key": n}`.           | `keys`             |
| `files::remove`                                      | Deletes one file, or an empty folder.                    | `write`            |
| `sqlite::query`                                      | One read-only `SELECT`, at most 50,000 rows.             | `sqlite`           |
| `http::request`                                      | An HTTPS request; `Request::header_with_key` puts a key in. | `http`          |
| `programs::run`, `Talk::start`                       | Runs a program once, or talks to it line by line.        | `run`              |
| `terminal::HiddenTerminal::start`                    | Starts a program unseen, sends keys, reads the screen.   | `terminal`         |
| `keyring::read`                                      | One keyring entry, its keys as handles.                  | `keyring`          |
| `keys::open`                                         | A handle for a declared key place.                       | `keys`             |
| `env::var`, `env::home`                              | A variable; the home folder.                             | `env`              |
| `env::language`, `env::in_language`                  | The language OTTY shows now; one of your translations.   | none               |
| `clock::now_ms`, `log::info` and the other levels    | The time; a line in the plugin's log.                    | none               |

A `Key` has `fingerprint()`, `has_prefix(text)`, `jwt_claims()` and `is_given_in_otty()` (whether
the user gave it in OTTY, [above](#a-refused-key)); the plugin never reads the key.

<Aside type="caution" title="Do not use HashMap or HashSet">
`std::collections::HashMap` and `HashSet` take a random seed, which makes the `.wasm` import
`wasi:random`, and OTTY refuses the plugin at install. Use `BTreeMap` and `BTreeSet`. A plugin may
import only `wasi:cli`, `wasi:io` and OTTY's own interfaces, so `std::fs`, `std::net` and
`std::time::SystemTime` do not work either: use the SDK's `files`, `http` and `clock`.
</Aside>

Each read gets a new instance of the plugin, so nothing is kept between calls. A call has 2 seconds
for the quick functions (`profiles`, `detect`, `version`, `logins`, `launch`), 120 seconds for
reading answers and sessions, and 90 seconds for limits and provider calls, with at most
64 MiB of memory. A call that traps or runs out of time fails alone; three failures in a row pause
the part.

## Test

`cargo test` runs natively, with no WebAssembly. The SDK's test host serves `fixtures/` as the home
folder, answers requests from canned answers, and checks every call against the permissions of the
part being tested, as OTTY does:

```rust
use otty_plugin_sdk::agents::{AccountFacts, Identity, Provider};
use otty_plugin_sdk::test_host::TestHost;

use crate::Example;

#[test]
fn numbers_read_the_balance_with_the_key_in_the_header() {
    let host = TestHost::new(env!("CARGO_MANIFEST_DIR"));
    host.answer(
        "GET",
        "https://api.example.com/v1/balance",
        200,
        br#"{"balance": 12.5, "currency": "USD"}"#,
    );
    let key = host.key("ex-made-up-key-0001");
    let account = AccountFacts { identity: Identity::default(), plan: None };

    let numbers = host
        .as_provider("example-cloud", || Example::numbers("example-cloud", &account, &key, &[]))
        .expect("the numbers");

    assert_eq!(numbers.left.map(|money| money.amount), Some(12.5));
    assert_eq!(
        host.requests()[0].header("authorization"),
        Some("Bearer ex-made-up-key-0001")
    );
}
```

## Build

```sh
rustup target add wasm32-wasip2
cargo build --release --target wasm32-wasip2
```

Keep the template's release profile: `opt-level = 3` (a plugin is built for speed, not size), `lto`,
one codegen unit, stripped. The `.wasm` may be at most 20 MiB.

## Try it in OTTY

<Steps>

1. Put the built `target/wasm32-wasip2/release/<crate>.wasm` as `<id>.wasm` in a folder with
   `otty-plugin.toml` and the icons.
2. In OTTY, open Plugins mode (from **All modes**, or **Settings** → **Plugins** → **Manage
   plugins…**) → **Add plugin from folder…** (the folder button on the left), type the folder,
   **Next**, **Install**. The checks and the install dialog are the same as for a release.
3. After a rebuild, copy the new `.wasm` into the folder and press **Reload** on the plugin's page.
   When the new copy asks for more, OTTY shows what changed first.

</Steps>

A plugin from a folder is marked **Local** and never updated on its own. **Show log** on its page
shows what it wrote with `log::*` and to stderr.

## Release

<Steps>

1. Set `version` in `otty-plugin.toml`, commit, and push a tag with the same version: `v0.1.0` or
   `0.1.0`. Other tags are ignored.
2. The template's workflow tests and builds the plugin, checks that the tag is semver and equals the
   manifest's version, and attaches `otty-plugin.toml`, `<id>.wasm` and the icons to the release.
3. Users paste your repository's link in **Add plugin…**. OTTY checks for new releases once a day.

</Steps>

- A release that asks for no new permission and has no new part installs on its own; one that does
  waits for each user's OK.
- Never change the files of a published release: OTTY refuses a release whose files differ from what
  it installed. Ship a new version instead.
- OTTY runs a plugin only when it knows every contract version in `[api]`, and installs the newest
  release it can run. Keep `[api]` at the oldest contract you need.

## Advice from the official plugins

The OTTY team reviews its own plugins against these rules; they are good rules for any plugin:

- Never print or log keys, tokens, prompts or session text.
- Never renew, write or delete another agent's login. In a provider part a refused login is
  `ReadError::LoginRefused`; the agent part's `login_refused` gives the need that makes the user
  log in again in the agent.
- Give every need a stable id and texts in OTTY's languages where you can, with English as the
  fallback.
- Never ask an agent's program for anything that changes its files. The OpenAI plugin never sends
  `thread/list` to `codex app-server`, because Codex then rewrites its own index of sessions.
- Ask only for the permissions you use, and write nothing but your own leftovers.
- Read tolerantly and count what you did not understand, so a format change shows as "format
  changed".

`plugins/build.sh` in the OTTY repository is for the OTTY team only: it builds an official plugin
into `assets/plugins/<id>/`, the folder users install it from with **Add plugin from folder…**. A
plugin of your own does not need it.
