# Blocks and shell event protocol

Shell integrations send lifecycle events in a DCS frame. The wire form is:

```text
ESC P otty-dcs;event-v2;h;<hex-encoded UTF-8 JSON> ESC \
```

Hex encoding keeps JSON text, quotes, newlines, and terminal-control-like input
from being interpreted as terminal framing. Both upper- and lower-case hex are
accepted. A frame is rejected if the hex payload is larger than 64 KiB, the
decoded JSON is larger than 32 KiB, an identifier is empty or larger than 512
bytes, or `seq` is zero. Command text is retained up to 16 KiB at a UTF-8
boundary and is marked as truncated beyond that limit.

Every JSON envelope contains these fields:

```json
{
  "v": 2,
  "event": "command_end",
  "terminal_session_id": "7dc5e10d092e4925a76041085d8f9ad2",
  "shell_instance_id": "7dc5e10d092e4925a76041085d8f9ad2:bash:4812:0",
  "seq": 18,
  "block_id": "7dc5e10d092e4925a76041085d8f9ad2:7dc5e10d092e4925a76041085d8f9ad2:bash:4812:0:7",
  "payload": {
    "exit_code": 7,
    "pipe_status": [0, 7],
    "cwd": "/work"
  }
}
```

`terminal_session_id` is generated by the application and registered with the
terminal model before the child shell starts. Events for another session are
discarded. `shell_instance_id` identifies one root or nested shell process and
`seq` is strictly increasing within that shell. Duplicate and stale sequence
numbers are ignored; a gap degrades the integration but is recovered using the
explicit block IDs and later prompt boundaries.

Supported events are:

- `shell_hello`: shell name, version, optional parent shell ID, and capabilities;
- `prompt_prepare`: stable ID and cwd for the next input block;
- `command_start`: exact block ID, command, cwd, and truncation flag;
- `command_end`: exact block ID, exit code or signal, pipeline status, optional
  next block ID, and cwd;
- `context_update`: a sparse shell-context update such as cwd;
- `shell_exit`: optional status and active block ID;
- `integration_error`: a non-sensitive diagnostic code.

The prompt itself is delimited separately with OSC 133 markers. `OSC 133;A ST`
starts prompt capture and `OSC 133;B ST` ends it. Integrations put these bytes in
Bash `\[`/`\]` or Zsh `%{`/`%}` non-printing prompt spans so the visible prompt
and line-editor column calculations do not change.

The shipped Bash and Zsh assets use only shell builtins for JSON escaping and
hex encoding. In simplified form, a valid emission is:

```bash
json='{"v":2,"event":"context_update","terminal_session_id":"session","shell_instance_id":"session:bash:4812:0","seq":1,"payload":{"cwd":"/tmp"}}'
hex=
LC_ALL=C
for ((i = 0; i < ${#json}; ++i)); do
  printf -v byte '%d' "'${json:i:1}"
  printf -v hex '%s%02X' "$hex" "$byte"
done
printf '\033Potty-dcs;event-v2;h;%s\033\\' "$hex"
```

```zsh
json='{"v":2,"event":"context_update","terminal_session_id":"session","shell_instance_id":"session:zsh:4812:0","seq":1,"payload":{"cwd":"/tmp"}}'
hex=
LC_ALL=C
for ((i = 1; i <= ${#json}; ++i)); do
  printf -v byte '%d' "'${json[i]}"
  printf -v hex '%s%02X' "$hex" "$byte"
done
printf '\033Potty-dcs;event-v2;h;%s\033\\' "$hex"
```

Protocol v1 is not a compatibility input. Legacy `otty-dcs;block` frames are
treated as unsupported DCS input and cannot create semantic events or blocks.
